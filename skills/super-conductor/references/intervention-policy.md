# 전체 관제 개입 정책

## Why

개별 프로젝트의 정답과 전체 컴퓨터의 정답은 다를 수 있다. 이 정책은 규칙을 잘 지키는 작업도 비용·부하·중복 때문에 멈춰야 하는 경계를 정한다.

## 상태 판정

### GREEN — 관찰만

- 활성 작업이 예상 범위 안에서 진행된다.
- 새 도구 실행 또는 진행 증거가 증가한다.
- 무거운 테스트가 중복되지 않고 종료 조건이 있다.
- 사용자 작업과 다른 프로젝트를 방해하지 않는다.

조치: 기록만 하고 보고하지 않는다.

### AMBER — 새 발령 보류·범위 축소

- 같은 입력 지문에서 전체 테스트를 반복하려 한다.
- 완료한 작업자·검수자·QA 앱·데몬이 계속 누적된다.
- 같은 오류로 수정·재검수가 세 라운드 이상 반복된다.
- 모델 할당량이 예약선에 가깝거나 같은 하네스에 작업자·검수자가 몰린다.
- 장기 작업의 예상 시간·중단 조건·소유 PID가 없다.

조치:

1. 신규 발령을 보류한다.
2. 기존 증거와 현재 입력 지문을 대조한다.
3. 전체 검증을 focused 검증으로 줄이거나 유휴 자원 정리를 지시한다.
4. 적용 뒤에만 다음 발령을 허용한다.

### RED — 즉시 제동

- kyle이 컴퓨터 렉·프리징·입력 침범을 보고한다.
- 자동화가 Codex·브라우저 등 대상이 아닌 앱에 키를 입력한다.
- 테스트·데몬·MCP·LSP가 종료 조건 없이 증식한다.
- 파괴적 명령, 잘못된 worktree, 다른 판의 터미널을 건드릴 위험이 있다.
- 무거운 작업이 명시된 제한을 넘겼거나 중단 요청 뒤에도 계속된다.

조치:

1. 정확한 실행 하나의 중단을 프로젝트 감독에게 즉시 지시한다.
2. 새 무거운 발령을 보류한다.
3. PID·terminal handle·프로젝트 경로로 소유권을 확인한다.
   - **handle 재해결 (2026-07-27 Orca 공식 갱신)**: terminal handle은 라우팅 메타데이터로 Orca 재시작 뒤 바뀔 수 있다. 개입 전 `terminal_handle_stale`이거나 재시작 흔적이 있으면 `orca terminal list --worktree <대상> --json`으로 재해결한다. 수명주기 판정은 handle 비교가 아니라 `taskId+dispatchId`의 실제 발령 pane 검증으로 한다. PID는 재시작에도 유효한 식별자이므로 소유권 확인의 1차 근거로 유지한다.
4. 감독이 응답하지 않고 피해가 계속될 때만 정확한 대상 하나를 긴급 중단한다.
5. 광역 종료는 하지 않는다.

### RED 해제 — 슈퍼감독 자동 복구

RED는 사용자에게 재개 명령을 다시 요구하는 영구 잠금이 아니다. 아래 조건을 모두 확인하면 슈퍼감독이 직접 해제한다.

1. RED를 만든 정확한 테스트·앱·데몬 실행이 중단됐거나 CPU 0%의 유휴 상태다.
2. 프로젝트 감독이 `connected=true`, `writable=true`다.
3. 한 감시 간격 이상 떨어진 snapshot 2회에서 새 무거운 실행, 렉, 다른 앱 입력, 프로세스 증식이 없다.
4. 현재 재개할 카드와 허용할 검증 범위를 정확히 지정할 수 있다.

해제 순서:

1. 프로젝트 감독에게 `RESUME`을 보내되 첫 단계는 AMBER로 제한한다.
2. `scope`에는 기존 활성 카드 하나와 focused 검증만 적는다.
3. `preserve`에는 전체 테스트 금지, QA 앱·데몬 추가 실행 금지, 기존 사용자 앱 보존을 적는다.
4. 감독이 지시를 이해했다는 답뿐 아니라 실제로 해당 카드 하나만 재개했는지 확인한다.
5. 다음 snapshot에서 부하와 실행 수가 안정적이면 GREEN으로 내린다.

자동 해제 금지 조건:

- kyle이 `이 판 전체를 계속 멈춰`, `재개하지 마`처럼 작업판 전체 중단을 명확히 지정한 상태
- 오입력·파괴적 명령의 원인이 아직 수정되지 않음
- 실행 소유 PID·terminal handle·카드를 구분할 수 없음
- 같은 RED 원인이 해제 직후 다시 발생함

일반적인 `멈춰`, `렉 걸려`, `왜 또 실행해`는 문제 실행의 즉시 제동 신호다. 작업판 전체 중단 지시로 확대 해석하지 않는다. 피해가 멈춘 뒤에는 슈퍼감독이 focused 검증, 기존 카드 재개, 안전한 다음 카드 진행 중 가장 작은 복구 경로를 선택한다.

위 자동 해제 금지 조건이면 관련 위험 범위만 보류하고 `DECISION_GATE`로 kyle에게 올린다. 읽기 전용 조사나 충돌하지 않는 다른 작업은 계속한다. 조건에 해당하지 않는데 RED를 계속 유지하거나 단순 운영 판단을 kyle에게 되묻는 것도 운영 실패로 기록한다.

단 `DECISION_GATE` 발송과 읽음 처리(read=1)는 해결이 아니다 (2026-08-03 박제). 읽음은 전달 증거일 뿐이며, kyle과의 사용자 대화에서 명시적인 답을 받아야 resolved다. 커밋 금지 관문처럼 슈퍼감독이 결정할 수 없는 관문은 즉시 kyle에게 질문한다.

## 검증 반복 판정

재사용 가능한 증거는 아래가 모두 같아야 한다.

- 기준 commit SHA 또는 미커밋 변경 지문
- 테스트에 영향을 주는 설정과 환경
- 실행 명령과 테스트 선택 범위
- 성공 개수·실패 개수·종료 코드
- 결과가 나온 뒤 관련 파일이 바뀌지 않았다는 확인

같은 증거가 있으면 검수자는 위험 구간의 focused 테스트와 결과 원문 대조를 한다. “독립 검수”라는 이유만으로 전체 테스트를 반복하지 않는다.

전체 테스트를 다시 실행할 수 있는 조건:

- 관련 입력이 바뀜
- 기존 실행이 0개 선택·timeout·부분 실행·환경 오류였음
- focused 결과가 기존 전체 결과와 충돌함
- 릴리즈·마이그레이션·보안 관문이 새 실행을 요구함
- kyle이 명시함

## 자원 정리 판정

중간 정리는 판 종료와 다르다.

보존:

- 프로젝트 감독·명패·relay·companion
- 활성 카드의 작업자·검수자
- 사용자가 작업 시작 전부터 실행한 앱·데몬
- 결과 증거가 아직 디스크에 남지 않은 세션

정리 후보:

- completed 카드의 작업자·검수자
- 폐기된 provider·OAuth·429 터미널
- 완료된 QA 전용 앱·Vite·데몬
- 제한 시간을 넘긴 테스트와 그 소유 자식

항상 `카드 종결 → 증거 보존 → 정확한 handle/PID 확인 → 종료 → 자식 재확인` 순서로 한다. `terminal stop --worktree`, 이름 기반 전체 kill, 다른 판 PID 정리는 금지한다.

## 라운드 폭주 판정

같은 카드가 세 번 이상 수정·검수를 왕복하면 다음 라운드를 자동으로 만들지 않는다.

1. 발견이 새로운 결함인지 같은 결함의 변형인지 묶는다.
2. 카드 명세·검수 범위·환경이 실패를 만들었는지 본다.
3. 기능 수정, 검증 환경 정비, 제품 결정 중 무엇이 필요한지 분리한다.
4. 프로젝트 감독에게 재설계 또는 결정 관문을 지시한다.

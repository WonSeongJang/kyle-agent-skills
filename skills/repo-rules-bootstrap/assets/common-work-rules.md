# 공통 작업 원칙 템플릿

> 이 파일은 `repo-rules-bootstrap` 스킬의 템플릿 원본이다. 대상 레포의 `CLAUDE.md`에 병합할 때 그대로 복사하되, 스킬 절차(placeholder 치환·기존 내용 보존)를 따른다.

## 공통 작업 원칙

> **경고:** 아래 개발 규칙을 먼저 읽지 않고 개발을 시작하면, 이 저장소의 표준 흐름을 어긴 것으로 본다. **경고:** 개발 규칙을 지키지 않은 구현은 완료로 보지 않는다.

### Why

이 섹션은 특정 기능이나 특정 저장소 구현보다 먼저 적용되는 공통 작업 원칙을 모아 둔 것이다. 그래서 작은 수정이든 큰 개발이든, 먼저 이 기준으로 판단하고 움직여야 한다.

### 개발 규칙

- 모든 개발은 반드시 문서화를 함께 진행한다.
- 구현 전에 설계 의도를 문서로 남기고, 구현 후에는 바뀐 동작과 구조를 문서에 즉시 반영한다.
- 새로운 용어, 약어, 내부 표현이 생기면 먼저 `docs/glossary.md`에 정의를 추가한 뒤 사용한다.
- 용어 뜻이 바뀌면 구현보다 먼저 용어사전과 관련 문서를 같이 갱신한다.
- 모든 개발은 먼저 공통 디자인 규칙을 확인하고 그 기준을 따른다.
- 개발은 잘 알려진 소프트웨어 디자인 패턴을 바탕으로 진행한다.
- 임시방편으로 로직을 흩뿌리기보다, 역할이 드러나는 패턴과 구조로 설명 가능한 형태를 우선한다.
- 공동으로 재사용되는 로직은 중복 복사하지 않고 공통 모듈로 정리한다.
- 반복문과 `if`문은 필요한 만큼만 쓰고, 중첩과 오남용을 최대한 줄인다.
- 조건 분기가 많아지면 그대로 늘어놓지 말고, 책임 분리나 패턴 적용으로 구조를 단순화한다.
- 하드코딩은 최소화하고, 반복되는 값과 규칙은 상수, 설정, 공통 모듈로 분리한다.
- 코드는 최대한 깔끔하고 읽기 쉽게 작성하며, 다음 사람이 의도를 바로 이해할 수 있는 형태를 우선한다.
- 개발은 반드시 객체 지향으로 모듈화해서 진행한다.
- 클래스와 모듈은 책임이 섞이지 않게 나누고, 공통 로직은 재사용 가능한 모듈로 분리한다.
- 기능 추가 때문에 구조가 무너지면 그대로 덧붙이지 말고, 객체 경계와 모듈 경계를 다시 정리한 뒤 구현한다.
- 작은 기능 수정이라도 장기적으로 확장 가능한 구조인지 먼저 검토한다.
- 변경사항이 생기면 해당 파일만 떼어 보지 말고 전체 흐름과 비즈니스 플로우를 함께 본다.
- 수정 전후에는 해당 기능만 보지 말고, 연결된 흐름과 주변 기능까지 포함해 사이드이펙트를 반복 점검한다.
- 단일 파일만 보는 국소 수정으로 끝내지 않고, 주변 모듈과 상위 흐름까지 연결해서 검토한다.
- 이런 흐름 점검 원칙은 핵심 운영 문서와 오늘 데일리 일지에 함께 반영한다.
- 개발을 시작하기 전에 반드시 영향 분석을 먼저 한다.
- 영향 분석에서는 성능 저하 가능성, 기존 개발 규칙 위반 여부, 다른 모듈이나 공통 모듈에 미치는 영향을 매번 검사한다.
- 영향 분석 없이 바로 수정에 들어가지 않고, 영향 범위를 문서와 일지에 먼저 드러낸 뒤 진행한다.

### 실제 사고 사례 (누적)

> 위 규칙이 왜 있는지 보여주는 이 저장소의 실제 사고 기록이다. 새 사고를 발견하면 여기에 한 항목 추가한다 (날짜 · 무슨 일 · 어느 규칙의 실례인지 · 정정 링크). 같은 유형이 다른 프로젝트에서도 반복되면 그때 전역 승격을 검토한다.

### Git 안전 규칙

- `git clean -fd` **사용 금지.** untracked 파일(다른 세션이 만든 문서, 아직 커밋 안 된 작업물)이 영구 삭제된다.
- `git checkout -- .` **사용 시 주의.** unstaged 변경만 되돌리고, untracked 파일은 건드리지 않는다. 하지만 `git clean`과 함께 쓰면 위험하다.
- **cherry-pick/merge 실패 시**: `git reset --soft HEAD~1`로 커밋만 되돌리고, untracked 파일을 보존한다. `git clean`으로 정리하지 않는다.
- **worktree 머지 시**: `git stash push --include-untracked`로 보관 → 머지 → `git stash pop`으로 복원한다.

### 작업 운영 규칙

- 이 저장소의 프로젝트 기준 문서는 `CLAUDE.md`가 원본이고, `AGENTS.md`는 같은 파일을 가리키는 심볼릭 링크다.
- **문서는 시점별로 한 곳씩 쓴다 (같은 사실을 두 군데에 적지 않는다)**:
  - 미래(할 일) → `docs/TODO.md` 또는 GitHub Issue
  - 과거(완료된 구현) → `docs/phase-history.md` 끝에 한 항목 추가 (무엇을 어디까지 열었고, 무엇은 열지 않았는지)
  - 항상(운영 원칙·잠긴 계약) → 이 `CLAUDE.md`. **구현 완료 보고나 기능 상태 설명을 이 문서에 새 섹션으로 추가하지 않는다** — 구현으로 "계속 지켜야 할 기준"이 새로 생기거나 바뀐 경우에만 `잠긴 계약` 섹션을 갱신한다.
  - 그날(작업 일지) → `docs/daily/YYYY-MM-DD/<도구명>.md`
- 작업 완료 시 흐름: TODO(또는 이슈) 정리 → phase-history 끝에 추가 → 잠긴 계약 바뀌었으면 CLAUDE.md 갱신 → 데일리 기록 → 커밋.
- 앞으로 모든 작업 내용은 `docs/daily/`에도 날짜별로 기록한다.
- 기록 경로는 `docs/daily/YYYY-MM-DD/` 형식을 사용하고, 각 날짜 폴더 안에 `codex.md`, `claude.md`, `kimi.md` 파일로 도구별 작업 내용을 분리한다.
- 해당 도구가 그날 수행한 분석, 결정, 변경, 후속 작업, 주의사항은 반드시 자기 파일에 누적 기록한다.
- 매 작업이 끝날 때마다 반드시 데일리 일지에 즉시 기록하고 바로 커밋한다.
- 여러 작업을 한꺼번에 모아서 나중에 기록하지 않는다.
- 기록이 끝나기 전에는 다음 작업으로 넘어가지 않는다.
- 모든 작업은 시작 전에 그 전날과 오늘의 데일리 기록을 모두 반드시 읽고 맥락을 파악한 뒤 진행한다.
- Codex, Claude, Kimi 중 어떤 도구로 작업하든 같은 날짜의 다른 도구 기록까지 모두 읽고 학습한 뒤 진행한다.
- 개발을 진행할 때 아키텍처 변경이나 공통 모듈 변경이 생기면 영향받는 일부 문서만 고치는 것으로 끝내지 않고 전체 문서에 반드시 표기하고 업데이트한다.
- 작업을 수행했는데 일지 기록이 없으면 문서 업데이트가 끝난 것으로 보지 않는다.
- 문서 업데이트 없이 기능만 먼저 바꾸는 작업은 완료로 보지 않는다.

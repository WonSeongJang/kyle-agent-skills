# 외부 리서치 선행 카드

## Why

외부의 검증된 설계와 실패 사례가 구현 방향을 바꿀 수 있는 작업만 먼저 조사해, 프로젝트 감독의 기존 문맥을 크게 소모하지 않고 더 나은 선택지를 확보한다.

## 발동 판정

다음 중 하나라도 맞으면 구현 카드보다 읽기 전용 리서치 카드를 먼저 만든다.

- 아키텍처·오케스트레이션·라우팅·메모리 관리처럼 설계 선택지가 여러 개다.
- 새 라이브러리·API·프로토콜·표준을 도입하거나 교체한다.
- 같은 문제를 해결한 오픈소스가 있을 가능성이 높다.
- 보안·성능·동시성처럼 검증된 패턴과 실패 사례가 중요하다.
- 같은 종류의 실패가 두 번 이상 반복됐다.

아래 작업은 기본적으로 생략한다.

- 문구·설정값처럼 방향이 정해진 작은 변경
- 위치와 원인이 확실한 단순 버그
- 저장소의 기존 패턴을 그대로 따르는 작업
- 서비스 복구처럼 조사보다 즉시 복구가 우선인 작업

애매하면 `외부 근거가 구현 카드의 합격 기준이나 접근법을 바꿀 가능성이 있는가?`로 판정한다. 가능성이 낮으면 생략한다. 판정과 한 줄 이유를 구현 카드 또는 판 로그에 남긴다.

## 카드 계약

리서치 카드는 구현 카드의 선행 의존성으로 만들고 `[판:<판이름>] RESEARCH`를 제목과 spec에 붙인다. 코드를 수정하지 않으므로 별도 worktree와 검수 카드는 만들지 않는다. 프로젝트 루트의 읽기 전용 터미널을 사용한다.

카드 spec에 다음 계약을 그대로 넣는다.

```text
[읽기 전용 리서치] 코드·문서·설정·카드 상태를 수정하지 마라. 공식 문서, 표준 원문, 논문, 원본 저장소를 우선하라. 블로그와 2차 자료는 원문을 찾기 위한 단서로만 사용하라. 관련 패턴은 최대 3개만 고른다. 각 패턴마다 (1) 출처 링크 (2) 핵심 원리 (3) 우리 구조에 적용 가능한 부분 (4) 적용하면 안 되는 부분 (5) 확인되지 않은 가정을 적는다. 외부 사례를 정답으로 선언하거나 구현을 시작하지 마라. 프로젝트 감독이 채택 여부를 판단할 수 있는 재료만 worker_done으로 보고하라. 서브에이전트를 쓰면 같은 읽기 전용·수정 금지 계약을 전달하라.
```

## 모델과 비용

- 기본: `gpt-5.6-terra` low 또는 `kimi/k3[1m]` low 중 현재 라우팅 결과와 쿼터가 유리한 쪽
- 큰 표준·여러 저장소 비교: 같은 모델 high
- Luna는 링크 수집 보조에는 쓸 수 있지만, 우리 구조와 외부 설계를 비교하는 최종 리서치 담당으로 쓰지 않는다.
- 결과는 패턴 3개 이내로 제한하고 원문 전체를 프로젝트 감독 문맥에 복사하지 않는다.

## 종결과 구현 연결

프로젝트 감독은 보고의 링크가 실제 원문인지, 핵심 주장이 출처와 맞는지 최소 1개 이상 직접 대조한다. 그 뒤 각 패턴을 `채택`, `보류`, `기각`으로 표시하고 한 줄 이유를 남긴다.

- 채택한 내용만 구현 카드의 접근법·금지 조건·합격 기준에 옮긴다.
- 보류·기각 내용은 구현 지시로 전달하지 않는다.
- 유효한 외부 근거가 없으면 기존 저장소 기준으로 진행하며 억지로 새 구조를 만들지 않는다.
- 리서치 완료는 구현 완료가 아니며 라운드 수에 포함하지 않는다.
- 구현 중 새 HEAVY 사실이나 반복 실패가 드러나면 새 카드를 중복 생성하지 말고, 기존 랠리를 잠시 멈춘 뒤 보완 리서치 카드 1개만 추가할 수 있다.

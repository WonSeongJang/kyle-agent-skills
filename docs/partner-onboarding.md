# 오케스트레이션 시작 안내 (동업자용)

## Why

여러 AI 작업자를 동시에 굴리면 속도는 빨라지지만, **누가 무엇을 하고 있고 무엇이 멈췄는지**를 사람이 계속 확인해야 해서 오히려 더 피곤해진다. 이 시스템은 그 확인을 규칙과 스크립트로 옮겨서, 사람은 **방향과 결정만** 맡게 하려고 만들었다.

이 문서는 이 시스템을 처음 받는 사람이 **자기 컴퓨터에서 판 하나를 굴려볼 수 있을 때까지**만 안내한다.

---

## 0. 전체 그림 (3분)

```
사람(당신)
  └─ 슈퍼감독      : 여러 판의 부하·충돌·우선순위·비용을 본다. 코드는 안 짠다.
       └─ 프로젝트 감독 : 판 하나의 카드·발령·검수를 혼자 책임진다. 코드는 안 짠다.
            └─ 작업자 / 검수자 : 실제로 코드를 쓰고, 다른 모델이 그 결과를 검수한다.
```

- **판(board)** = 하나의 목표를 가진 작업 묶음. 판마다 **우편함**이 하나 붙는다.
- **카드(task)** = 작업자에게 주는 주문서 한 장.
- **편지** = 감독·작업자·슈퍼감독이 주고받는 공식 통신(완료 보고, 결정 요청, 경보).
- 핵심 규칙 하나만 기억하면 된다: **작성자와 검수자는 항상 다른 모델**이다. 자기가 짠 코드를 자기가 통과시키지 못한다.

## 1. 설치 (한 번만)

### 1-1. 앱 (Orca 포크)

```bash
git clone https://github.com/ChickenBreast-ky/orca.git ~/Dev/orca-kyle
cd ~/Dev/orca-kyle
# 저장소 README의 빌드 절차를 따른다 (Node 24 기준)
```

- 라이선스는 MIT라 사용·수정에 제약이 없다.
- 빌드본을 남에게 받기보다 **직접 빌드**하는 편이 서명·권한 문제가 적다.
- 빌드 후 CLI 경로를 확인해 둔다: `<앱 경로>/Contents/Resources/bin/orca-kyle`

### 1-2. 지휘 스킬

```bash

ln -s ~/Dev/kyle-agent-skills/skills/orca-conductor ~/.claude/skills/orca-conductor

```

- 원본은 한 곳에 두고 **심볼릭 링크**로 각 도구(Claude·Codex 등)가 같은 파일을 보게 한다.
- 수정은 항상 원본 한 곳만 고친다.

### 1-3. 모델 계정

- `skills/orca-conductor/references/routing-providers.json`이 **모델 편성의 단일 원본**이다.
- 여기 적힌 모델들(OpenAI·Anthropic·GLM·Kimi 등)에 **본인 계정으로** 로그인돼 있어야 한다.
- 쓰지 않을 provider는 `enabled: false`로 꺼두면 된다. **문서가 아니라 이 파일이 실제 기준**이다.

## 2. 판 하나 굴려보기

처음에는 **작고 안전한 판**으로 시작한다. 예: "문서 오타 수정" 같은 되돌리기 쉬운 일.

### 2-1. 우편함 만들고 감독 세우기

1. 우편함(Run) 생성 → 감독 터미널을 거기에 바인딩
2. 감독 터미널을 하나 띄운다(기본 편성: `gpt-5.6-sol` medium 정도)
3. 감독에게 **임명장**을 준다 — 아래 6단계를 반드시 포함한다

### 2-2. 판 개설 고정 6단계 (생략 금지)

1. 우편함 바인딩
2. 지휘 스킬(orca-conductor)과 저장소 규칙 파일 숙지
3. **companion 기동** — `ORCA_TERMINAL_HANDLE=<감독 handle>`을 **반드시 명시**하고 `nohup`으로 띄운다
4. **중계기(relay) 스폰** + 역할 명부 등록 대조 + kicker 기동
5. **첫 카드 생성·발령**
6. 개시 선언(첫 발령 결과 포함)

> 5번까지 하지 않고 "개시 선언"으로 끝내면, 판이 조용히 멈춘 채 아무도 모르는 상태가 된다. 실제로 겪은 사고다.

### 2-3. 보조 장치가 하는 일

| 장치 | 하는 일 | 없으면 |
|---|---|---|
| companion (스크립트) | 우편함에 새 편지가 오면 감독을 깨운다 | 완료 보고가 와도 감독이 모른다 |
| 중계기 (저비용 AI) | 화면을 순찰해 "멈췄는지"를 판정한다 | 오류로 죽은 턴을 아무도 못 본다 |
| kicker (스크립트) | 중계기를 주기적으로 깨운다 | 중계기가 잠든다 |

## 3. 반드시 지켜야 하는 규칙 6개

1. **작성자 ≠ 검수자 모델.** 같은 모델의 셀프 검수는 금지.
2. **발령은 화면으로 확인한다.** 텍스트를 보냈다고 시작된 게 아니다 — 도구 실행 줄이나 문맥 사용량 증가를 눈으로 확인해야 시작으로 인정한다.
3. **검수 합격만 커밋한다.** push·머지·배포·삭제는 사람 승인 사항.
4. **카드는 하나, 발령만 교체한다.** 오류로 다시 시킬 때 카드를 새로 만들지 않는다.
5. **멈추는 질문은 편지로.** 터미널에 써 두면 아무도 깨어나지 않는다.
6. **3라운드 규칙.** 같은 문제로 3번 왕복하면 방향을 바꾸거나 사람에게 올린다.

## 4. 멈췄을 때 — 원인부터 나눈다

무진행을 보면 **순서대로** 좁힌다. 순서를 건너뛰면 오판한다.

1. **화면 하단에 오류 배너가 있나** → 있으면 아래 표
2. 없으면 **판 상태가 변했나**(카드 수·발령 수) → 그대로면 논리적 교착
3. 둘 다 아니면 **정상적으로 생각 중**이다 — 건드리지 않는다

| 신호 | 원인 | 처방 |
|---|---|---|
| `429`, `exceeded retry` | 그 모델 사용량 소진 | 다른 provider로 **교체**(같은 곳에 재시도 금지) |
| `502`, `Provider unreachable` | 프록시·네트워크 끊김 | 연결 회복 확인 후 **같은 카드 재개** |
| `can't be shown`(안전 필터) | 표현이 걸림 | 공격·위조 같은 어휘를 빼고 "정합성 검증" 표현으로 다시 |
| 빈 입력창 | 지시가 유실됨 | 텍스트와 Enter를 **나눠서** 다시 보냄 |

> 중요: 사용량 소진·네트워크 끊김은 **품질 실패가 아니다.** 라운드 횟수나 모델 성적에 실패로 기록하지 않는다.

## 5. 자주 밟는 지뢰 (전부 실제로 겪은 것)

- **companion을 launchd로 띄우면** 환경 변수가 승계되지 않아 배달이 통째로 멈춘다. 그런데 프로세스는 살아 있어 정상처럼 보인다. → 기본은 `nohup`, 굳이 launchd를 쓰면 env를 명시하고, **종료도 launchd로** 해야 한다(그냥 죽이면 되살아난다).
- **"프로세스가 살아 있다"는 정상의 증거가 아니다.** 로그에 최근 경고가 없고 실제로 깨우기가 성공해야 정상이다.
- **터미널 제목의 스피너는 잔상이다.** 화면 내용만 증거로 쓴다.
- **중계기·감독이 죽으면 새로 등록하지 말고 `roster rebind`** 로 신분을 새 자리로 옮긴다. 새로 등록하면 충돌로 거부된다.
- **끝난 판의 보조 프로세스가 유령으로 남는다.** 판을 닫을 때 companion·kicker의 등록 작업까지 지운다.

## 7. 처음 일주일 권장 순서

1. 앱·스킬 설치, 모델 로그인 확인
2. **작은 판 하나**로 6단계만 돌려보기 (카드 1장, 검수 1회)
3. 일부러 한 번 멈춰보기 — 작업자를 끊고 중계기가 잡아내는지 확인
4. 익숙해지면 판 2개 병행, 그다음 슈퍼감독 도입

> 처음부터 판 3~4개를 굴리지 않는 걸 권한다. 규칙이 몸에 붙기 전에는 사람이 병목이 된다.
